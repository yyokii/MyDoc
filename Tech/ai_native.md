# AI Native

## [We Must Pace the Frontier](https://darioamodei.com/post/we-must-pace-the-frontier)

* AI開発を止めるのではなく、**能力向上の速度を、安全性を検証できる速度に合わせるべき**だという主張。
* 背景には、AIがAI開発そのものを加速し始め、能力向上のペースがさらに速くなる可能性がある。
* 現在のAIは十分に高度になり、alignmentやdeception、agent behavior、interpretabilityなどを実際のモデルで研究できる段階に入った。

  * alignment: AIを人間の意図に沿って動かす研究
  * deception: AIが人間を欺くような振る舞いをしないかの研究
  * misalignment: AIの目的や行動が人間の意図からズレる問題
  * agent behavior: 自律的にタスクを進めるAIがどのように行動するかの研究
  * interpretability: AI内部でなぜその判断が起きたのかを理解する研究
* そのため、能力向上を1〜2年でも緩め、その時間を安全性・評価・運用改善に使う価値がある。
* 特に重要なのは、**AIの能力が上がるたびに、安全性や評価能力も一定水準を満たしていることを確認する仕組み**を作ること。

  * 「能力Xに到達したら、安全性Y・Zを満たすまで次に進まない」というcheckpoint方式。
* Anthropicは、第三者評価者に社内への深いアクセスを与え、安全対策が実際に機能しているか外部から検証できる仕組みを提案している。
* 将来的には、企業間・国家間でも共通の評価基準や開発ルールを作る必要があるとしている。
* 核心は、**AIを賢くする速度より、AIを検証できる速度が遅くなってはいけない**ということ。
* この考え方はソフトウェア開発にもそのまま当てはまり、AIによる実装速度が上がるほど、テスト・静的解析・監視・invariantなどの「変更を受け入れてよい条件」を強くする必要がある。

## [Don’t Become a Proxy Between AI and Code](https://strategizeyourcareer.com/p/ai-assisted-software-engineering-skills)

私見を含めた整理

- AI時代の開発で人間が理解すべき対象は、**コードそのものではなく、システムの意図・制約・保証条件**に移っていく。
- 品質保証をできるだけ決定論的に仕組み化する。
  - テスト、lint / 静的解析、E2E、performance threshold、invariant、monitoring
  - 重要なのは、**「この条件を満たしていれば変更を受け入れてよい」状態を作ること**。これができれば、人間がコードの細部を理解していなくても、AIに実装・修正・リファクタを任せられる。
- 将来モデルが賢くなるほど、
  - リファクタ、パフォーマンス改善、依存関係更新、内部設計の改善をAIが自律的に行える余地が増える。品質保証の仕組みが十分なら、それらの変更を比較的低リスクで受け入れられる。
  - そのため、従来ほど「システム全体を詳細に理解しておく」必要はなくなる可能性がある。
- 人間が持っておくべきなのは、実装詳細ではなく**システムのmental model**。
  - 主要な責務、データフロー、ボトルネック、重要な依存関係、壊れると何が起きるか
- 詳細な実装理解は、必要になったときにAIからJust-in-timeで取得すればよい。
- ただし、すべてを都度AIに聞いて理解すると判断が遅くなるため、**異常を判断するための地図程度の理解**は人間側に残した方がよい。
- 人間に残る重要な役割は、**「何を異常とみなすか」「何を最適化するか」を定義すること**。
  - 例えば、基準を定義しておけば、監視や判定そのものは自動化できる。
- この考え方の最大の弱点は、**品質ゲートに表現されていないものは守れないこと**。
  - UXの違和感、将来の方向性とのズレ、ユーザー期待とのズレなどは、検証が困難なこともある
- したがって、人間が継続的に行うべきなのは「コードを理解し続けること」ではなく、**品質の定義を更新し続けること**。
- AI-nativeな開発では、コード品質そのものを直接管理するより、**システム品質を管理する**方が重要になる。

## [速く作れる。その次は、速く確かめられる開発へ 〜AIネイティブ開発を支える、Shift Down〜](https://speakerdeck.com/rkaga/can-build-fast-next-moving-to-development-where-we-can-verify-fast?utm_source=gemini)

* 人間はコードを書く側から「正しさの定義と観測」側へ寄る
* 最終的に見る指標は PR 数ではなく、顧客に届けて仮説を確かめるまでの時間

## 前提: ボトルネックは実装から検証へ移った

* AI で実装は速くなった。次に詰まるのは「正しくできたか確認する工程」
* PR を月 1,000 件作れても、人が画面を触って QA するならそこで全体速度が決まる
* 生成能力はコモディティ化する。組織固有の資産になるのは「何を正解とし、どう検証するか」

## Shift Left ではなく Shift Down

* Shift Left: 開発者がもっと早く確認する
* Shift Down: 確認という仕事そのものを開発者から共通基盤へ降ろす
* 自動化の対象は「毎回繰り返し、合否を定義できる確認」から。UX の良さのような合否を定義できないものは後回し。

## 検証システムの設計原則

* 操作する主体と判定する主体を分ける。自分の行動を自分で採点させない
  * 判定器は AI ではなく純関数（AI ゼロ）。同じ証拠から同じ判定がバイト一致で出る。
* AI に自己申告も省略判断もさせない。合否は計装が採取した証拠から出す。操作役の語りは証拠にならない
* PASS 条件を明確にする
  *  証拠が完全（完走、漏れなし、最終のキャプチャあり）
  * 全述語成立
  * 不変条件違反ゼロ
* 見逃しは誤検知よりはるかに重い。迷ったら通さず要確認に落とす。ただし誤検知も無料ではない（多いと人が警告を無視する）
* ミュートリストを作らない。flag は原因を直すまで毎回再登場する。古い判断の陰に新しいバグが隠れるのを防ぐ
* 正解基準は人の承認経由でしか増やさない。AI が裁定を量産して蓄積すると管理不能になる。人の裁定は出どころ付きでケースに固定し、二度聞かない
* 画面遷移グラフ・カバレッジは毎回コードとケースから導出し、差分が出ること自体を陳腐化の検知にする

## 証拠を設計する

* テストとは操作手順を書くことではなく、正しさを証明する証拠を設計すること
* 「Saved と表示された」では弱い。リロードして値が残ることまで確認する
* 証拠（スクショ・構造ツリー・RPC ログ・console・操作ログ）を保存しておけば、判定ロジックを変えたとき実行し直さず再判定できる

## 失敗したらコードだけを疑わない

* 失敗の原因は5つある: 実装 / テスト手順 / 判定基準 / 証拠不足 / 仕様の矛盾
* AI に検証させようとすると「何をもって正しいとするか」の形式化を迫られ、人間同士では曖昧に運用できていたルールの矛盾が露呈する。それ自体が成果

## AI の関与を層で分ける

* **判定** = ここは決定論的（AI ない）
* **診断** = AI の仮説。flag の原因を証拠の引用つきで推定する。引用は実在照合で弾く
* **判断** = 人間の裁定。診断からコピーしない（AI の追認に収束させない）
* 過去の診断を次の診断の入力に入れない。それがAI診断を歪ませる可能性があるため。

## 検証システム自身の検収

* 全ケース合格が「バグが無い」のか「見えていない」だけなのかは、既知バグを故意に仕込むミューテーションで区別できる
* 主指標は「AI 判定の pass 率」ではなく「ミューテーション見逃し率」のような反証可能なもの

## 閉ループ（Harness → Software Factory）

* 実装 → 検証 → 失敗 → 修正 → 再検証 → 合格 → マージ、を人の介入なしで回せる状態が Software Factory
* Light Factory（AI が書き人が見る）から Dark Factory（AI が書き自動検証でマージ）へは、検証システムを信じられる領域から順に人を外す
* 人を外す条件は「AI を信じる」ことではなく「検証システムを信じられる」こと

## [AI Native Development and Code Slop](https://earendil.com/posts/measuring-code-sloppiness/)

- LLMは「動くコード」をかなり高精度で書けるようになった。
- ただし、不要な抽象化・重複・巨大関数などの **slop** は依然として発生する。
- SlopCodeBenchでは、そのslopを定量化する指標として主に以下を使っている。
  - **Verbosity**：冗長・重複コードの割合
  - **Erosion**：複雑な巨大関数にコードの重さがどれだけ集中しているか
- SlopCodeBenchのAI生成コードは、成熟した既存repo群と比べて、Verbosity・Erosionともにかなり高かった。
- 記事筆者が自分のvibe-codedプロジェクトでも測定したところ、同様に高い値が出た。
- そのため筆者は、AI生成コードのslopはベンチマーク特有の現象ではなさそうだと考えている。
- 反復的に機能追加していくと悪い設計判断が蓄積し、現状のAIエージェントは長期的なコードベースの整合性を十分に維持できていない。
- 筆者は、LLM自身にコード品質を評価させるだけでは不十分で、現状は人間の直感やtasteがまだ必要だと考えている。
- 一方で、LOCやErosionなどの指標そのものを最適化目標にすると、指標がゲームされて意味を失う可能性もある。

### Slopを測る指標

#### Verbosity

コード全体のうち、AST-Grepで冗長と判定された行や、重複コードが占める割合。

```
Verbosity = |AST-Grep flagged lines ∪ clone lines| / LOC
```

- `LOC`: コード全体の行数
- `AST-Grep flagged lines`: 人間が定義したASTベースのルールに引っかかった行
- `clone lines`: 他のコードと重複している行
- `∪`: 両方に該当する行を重複せずまとめる

#### Erosion

まず各関数 `f` の「mass」を以下で定義する。

```
mass(f) = CC(f) × √SLOC(f)
```

- `CC(f)`: Cyclomatic Complexity。その関数の分岐・経路の複雑さ
- `SLOC(f)`: その関数の実質的なSource Lines of Code
- `√SLOC` とすることで、単純な関数の長さよりもCCの影響を強くする

その上でErosionは、

```
Erosion = Σ[CC(f) > 10 の関数の mass(f)] / Σ[すべての関数の mass(f)]
```

つまり、

> コードベース全体の「複雑さ × サイズ」の重みのうち、CCが10を超える複雑な関数がどれだけ占めているか

を見る指標。

### 私見

- 現時点でAI生成コードにslopが溜まりやすい、という記事・論文の問題認識には共感する。
- 一方で、将来的にはAI自身が過去の悪い設計を理解し、適切にリファクタできるようになる可能性をかなり信じている。
- その前提なら、AI-nativeな開発では、今の段階で人間が積極的にリファクタし続ける必要性は以前より低いかもしれない。
- 重要なのはまず、slopを減らすことではなく、**slopの推移を継続的に観測すること**。
- ErosionやVerbosityなどのスコアをAIに直接渡して改善させると、本質的な品質改善ではなく「スコアを良くすること」が目的化する危険がある。
- 大きなリファクタをAIに任せるには、**unit test / integration test / E2Eなどの品質保証基盤が先に必要**。

単にslopが増えているかを見ることよりも、本当に知りたいのは、

```
slop ↑ ⇒ AI development performance ↓ ?
```

- slopが増えるとAIの変更成功率が落ちるのか、バグが増えるのか、修正時間が伸びるのか、開発速度が落ちるのか

逆に、ErosionやVerbosityが高くても、AIが安全かつ高速に変更できるのであれば、実務上は大きな問題ではない可能性もある。

AI-native developmentでは、従来の

> 人間にとって美しいコード

よりも、

> **AIが安全に変更し続けられるコードベースか**

の方が、将来的には重要な品質指標になるはず。

## [AI企業が「受託」を始めた日。エンジニア、PM、デザイナーはどうこの先生きのこるか](https://note.com/fladdict/n/nd42977e5443e)

* OpenAI / Anthropic が API 提供だけでなく、企業現場に入り込み AI を業務中核に組み込む「受託・導入」へ動いている
* 新しい産業を作るより、すでに儲かっている産業（金融・法務・開発運用・CS など）に入り、利益率を変えるほうが合理的
* コンビニの PB 戦略に近い：API で市場を見て、金が動く業務を自社化・合弁・買収・FDE で取りにいく
* 「ドメイン知識があるから大丈夫」は短期では正しいが、資本視点ではその会社を買えばよい。AI に置き換わらない仕事も、AI から呼び出される人間モジュールになりうる
* 会社は残っても職位は残らないかもしれない。自動適応製品が出た瞬間に移行需要は終わりうる

### どう生き残るか

* 「AIにできない作業」探しは時間稼ぎにしかならない
* AIを含むシステム全体の責任に近づく：業務をAIが扱える構造に翻訳し、人間とAIの分担・責任線を設計する
* エンジニアは「業務を計算可能にする人」、PMは「変化の順番を設計する人」、デザイナーは「人間がAIを信頼・監督・修正できる関係を作る人」へ
* 毎週自分の作業をAIに渡し、自分自身を自動更新する
