# AI Native


## [AI Native Development and Code Slop](https://earendil.com/posts/measuring-code-sloppiness/)

## 記事の内容

- LLMは「動くコード」をかなり高精度で書けるようになった。
- ただし、不要な抽象化・重複・巨大関数などの **slop** は依然として発生する。
- SlopCodeBenchでは、そのslopを定量化する指標として主に以下を使っている。
  - **Verbosity**：冗長・重複コードの割合
  - **Erosion**：複雑な巨大関数にコードの重さがどれだけ集中しているか
- SlopCodeBenchのAI生成コードは、成熟した既存repo群と比べて、Verbosity・Erosionともにかなり高かった。
- 記事筆者が自分のvibe-codedプロジェクトでも測定したところ、同様に高い値が出た。
- そのため筆者は、AI生成コードのslopはベンチマーク特有の現象ではなさそうだと考えている。
- 反復的に機能追加していくと悪い設計判断が蓄積し、現状のAIエージェントは長期的なコードベースの整合性を十分に維持できていない。
- 筆者は、LLM自身にコード品質を評価させるだけでは不十分で、現状は人間の直感やtasteがまだ必要だと考えている。
- 一方で、LOCやErosionなどの指標そのものを最適化目標にすると、指標がゲームされて意味を失う可能性もある。

## Slopを測る指標

### Verbosity

コード全体のうち、AST-Grepで冗長と判定された行や、重複コードが占める割合。

```
Verbosity = |AST-Grep flagged lines ∪ clone lines| / LOC
```

- `LOC`: コード全体の行数
- `AST-Grep flagged lines`: 人間が定義したASTベースのルールに引っかかった行
- `clone lines`: 他のコードと重複している行
- `∪`: 両方に該当する行を重複せずまとめる

### Erosion

まず各関数 `f` の「mass」を以下で定義する。

```
mass(f) = CC(f) × √SLOC(f)
```

- `CC(f)`: Cyclomatic Complexity。その関数の分岐・経路の複雑さ
- `SLOC(f)`: その関数の実質的なSource Lines of Code
- `√SLOC` とすることで、単純な関数の長さよりもCCの影響を強くする

その上でErosionは、

```
Erosion = Σ[CC(f) > 10 の関数の mass(f)] / Σ[すべての関数の mass(f)]
```

つまり、

> コードベース全体の「複雑さ × サイズ」の重みのうち、CCが10を超える複雑な関数がどれだけ占めているか

を見る指標。

## 私見

- 現時点でAI生成コードにslopが溜まりやすい、という記事・論文の問題認識には共感する。
- 一方で、将来的にはAI自身が過去の悪い設計を理解し、適切にリファクタできるようになる可能性をかなり信じている。
- その前提なら、AI-nativeな開発では、今の段階で人間が積極的にリファクタし続ける必要性は以前より低いかもしれない。
- 重要なのはまず、slopを減らすことではなく、**slopの推移を継続的に観測すること**。
- ErosionやVerbosityなどのスコアをAIに直接渡して改善させると、本質的な品質改善ではなく「スコアを良くすること」が目的化する危険がある。
- 大きなリファクタをAIに任せるには、**unit test / integration test / E2Eなどの品質保証基盤が先に必要**。

単にslopが増えているかを見ることよりも、本当に知りたいのは、

```
slop ↑ ⇒ AI development performance ↓ ?
```

- slopが増えるとAIの変更成功率が落ちるのか、バグが増えるのか、修正時間が伸びるのか、開発速度が落ちるのか

逆に、ErosionやVerbosityが高くても、AIが安全かつ高速に変更できるのであれば、実務上は大きな問題ではない可能性もある。

AI-native developmentでは、従来の

> 人間にとって美しいコード

よりも、

> **AIが安全に変更し続けられるコードベースか**

の方が、将来的には重要な品質指標になるはず。

## [AI企業が「受託」を始めた日。エンジニア、PM、デザイナーはどうこの先生きのこるか](https://note.com/fladdict/n/nd42977e5443e)

* OpenAI / Anthropic が API 提供だけでなく、企業現場に入り込み AI を業務中核に組み込む「受託・導入」へ動いている
* 新しい産業を作るより、すでに儲かっている産業（金融・法務・開発運用・CS など）に入り、利益率を変えるほうが合理的
* コンビニの PB 戦略に近い：API で市場を見て、金が動く業務を自社化・合弁・買収・FDE で取りにいく
* 「ドメイン知識があるから大丈夫」は短期では正しいが、資本視点ではその会社を買えばよい。AI に置き換わらない仕事も、AI から呼び出される人間モジュールになりうる
* 会社は残っても職位は残らないかもしれない。自動適応製品が出た瞬間に移行需要は終わりうる

### どう生き残るか

* 「AIにできない作業」探しは時間稼ぎにしかならない
* AIを含むシステム全体の責任に近づく：業務をAIが扱える構造に翻訳し、人間とAIの分担・責任線を設計する
* エンジニアは「業務を計算可能にする人」、PMは「変化の順番を設計する人」、デザイナーは「人間がAIを信頼・監督・修正できる関係を作る人」へ
* 毎週自分の作業をAIに渡し、自分自身を自動更新する
